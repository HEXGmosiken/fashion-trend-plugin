# trend-lab 插件详解

> 这份文档讲的是「怎么实现的」，不是「怎么用」。怎么用看根目录的 `README.md`。
> 面向汇报：每一节都可以单独拿出来讲。

---

## 0. 一句话

trend-lab 是一个**服装趋势分析插件**：把文章变成一份能翻、能查、能复核的趋势报告。

它有两个入口：命令行和代码 API。网页只是它输出的产物，不是它本身。

---

## 1. 它对应任务书的哪几条

| 任务要求 | 插件里的落点 | 具体位置 |
|---|---|---|
| 核实资料，保留原始链接 | 每条证据都有 `url` 和 `excerpt`，报告里可点击回原文 | `schema.ts` 的 `EvidenceSchema` |
| 核对描述，图文一致 | 编码规则 + 原文摘录是必填项，描述不得超出摘录 | `claims.json` 的 `codingRule` |
| 验证趋势，要前后可比 | 双时间窗 + Wilson 区间 + 最小样本量 | `metrics.ts` / `findings.ts` |
| 说明不确定，列反证 | 置信度三档 + 反证清单 + 局限说明 | `findings.ts` |
| 逐条检查报告 | 16 类自动检查 | `audit.ts` |
| 独立演示入口 | `pnpm ingest` / `pnpm real` / `pnpm demo` | `src/cli/index.ts` |
| 写清输入输出与启动 | `README.md` + 本文件 | — |
| 便于主项目调用 | `src/index.ts` 导出 `analyze()` 与 `render.*` | `src/index.ts` |

## 2. 三条命令，三个目录

```bash
pnpm ingest   # 自动模式：投喂文章，抽趋势      → reports/auto/
pnpm real     # 精细模式：人工编码 + 双时间窗   → reports/curated/
pnpm demo     # 示例数据：验证链路              → reports/demo/
```

跑完会生成一个总入口：

```
reports/
├── index.html          三种模式的目录页
├── site.json           目录页的数据
├── auto/               deck.html / trends.md / trends.json
├── curated/            deck.html / trends.md / report.md / report.json / evidence.csv / findings.csv
└── demo/               deck.html / report.md / report.json / evidence.csv / findings.csv
```

**为什么分三个目录**：三份报告的数据源和结论完全不同，混在一起会看错。`index.html` 是唯一入口，从那里点进去。

## 3. 架构总览

```
                    ┌─────────────────┐
  articles.json ───▶│  core/auto.ts    │──┐
                    │  词表命中/聚合    │  │
                    └─────────────────┘  │
                                          ▼
                    ┌─────────────────┐  ┌──────────────────┐
  evidence.json ───▶│ core/report.ts   │─▶│  TrendBook       │
  claims.json   ───▶│ 去重→指标→结论→审计│  │  (趋势单元)       │
  sources.json  ───▶└─────────────────┘  └──────────────────┘
                             │                     │
                             ▼                     ▼
                    ┌─────────────────┐  ┌──────────────────┐
                    │ render/markdown  │  │ render/magazine   │
                    │ render/json      │  │ render/trend-md   │
                    │ render/csv       │  │ render/site       │
                    └─────────────────┘  └──────────────────┘
                             │                     │
                             ▼                     ▼
                      report.md/json/csv      deck.html / trends.md
```

两条摄入路径：

- **自动路径**：`articles.json → auto.ts → TrendBook`，不经过 claims。
- **精细路径**：`evidence + claims → report.ts → findings → BuildDeck → TrendBook`。

两条路径最后都汇到同一套渲染器。

## 4. 一次 `pnpm ingest` 发生了什么

以仓库里 50 篇文章为例，逐步拆开：

**第一步：读文章**（`cli/index.ts`）
读 `data/articles.real.json`，得到 50 个对象，每个带标题、链接、日期、来源、正文。

**第二步：切句**（`core/auto.ts` 的 `sentences()`）
按中文句号、问号、感叹号、英文句点切分，丢掉短于 24 字的碎片、以 `#` 开头的标题行、以 `Mrs.` 之类缩写结尾的半句。

**第三步：词表扫描**
拿 52 个中英双语词（`TERMS`）逐条正则匹配。每个词记录：出现在哪些文章、哪些句子、总次数。

**第四步：按板块聚合**
每个词属于一个板块（廓形/结构/材质/色彩/美学/场景）。同板块内按「出现篇数」排序，取前 3。门槛是 `max(2, 文章数 × 6%)`，50 篇时等于 3 篇。

**第五步：生成趋势单元**
每条趋势包含：名称、英文代号、板块、标签、一句判断、三条数据要点、同篇共现词、最多 3 条原文引用、最多 4 张配图。

**第六步：渲染**
`renderMagnetic` 把 TrendBook 渲染成 `deck.html`，`renderTrendMarkdown` 渲染成 `trends.md`，同时把这份报告登记进 `reports/index.html`。

全程没有模型参与，同样的输入永远得到同样的输出（有单测验证）。

## 5. 每个文件干什么

### 5.1 入口层

| 文件 | 作用 | 关键点 |
|---|---|---|
| `src/cli/index.ts` | 命令行入口 | 参数解析、目录约定、写文件、更新 `reports/index.html` |
| `src/index.ts` | 对外 API | 只导出 `analyze()`、`buildDeckModel()`、`render.*`，主项目只需要这一个文件 |
| `package.json` | 脚本 | `demo` / `ingest` / `real` / `analyze` / `validate` / `check` / `test` / `typecheck` |

### 5.2 数据层

| 文件 | 作用 | 关键点 |
|---|---|---|
| `core/schema.ts` | 输入契约 | 用 Zod 定义 7 种对象：来源、证据、命题、时间窗、板块配置、版式配置、文件格式 |
| `core/io.ts` | 读文件 | JSON 解析 + 校验，报错会指出字段路径，而不是抛一堆堆栈 |
| `core/types.ts` | 输出类型 | 指标、结论、审计问题、报告、目录页 |

**为什么用 Zod**：坏数据必须在入口断掉。比如日期写成 `2026/10/01`，报告会直接拒绝启动，而不是在统计时算出 NaN。

### 5.3 分析层

| 文件 | 作用 | 关键点 |
|---|---|---|
| `core/normalize.ts` | 去重 | URL 归一、标题分词、三层重复判定 |
| `core/metrics.ts` | 统计 | Wilson 区间、占比比较 |
| `core/findings.ts` | 结论 | 从编码算占比，按规则定置信度，同时生成反证 |
| `core/audit.ts` | 质量检查 | 16 类检查，分错误/警告/提示 |
| `core/report.ts` | 流水线 | 去重 → 结论 → 审计 → 组装 Report |
| `core/present.ts` | 语言层 | 把「50.0%（8/16，95% CI…）」翻译成「50%，16 篇中 8 篇」 |

### 5.4 自动抽取

| 文件 | 作用 |
|---|---|
| `core/auto.ts` | 词表、切句、聚合、生成 TrendBook；也负责把文章包成一份最小 Report 给渲染器用 |

词表一共 52 个词，覆盖六个板块，中英双语正则。加词就能加能力，不需要改算法。

| `data/trends.json` | 生成物：引用、词频、图片都是脚本抓的 |
| `data/evidence.real.json` | 50 条证据台账，精细模式的输入 |

### 5.8 工具脚本（`_tools/`）

| 脚本 | 作用 |

| `images.py` | 抓文章头图，只保留 700×420 以上，压到 1400 宽 |
| `build_trends.py` | 从语料里抽引用、算词频、挂图片，生成 `trends.json` |
| `ingest.py` | 把 markdown 语料解析成证据 JSON |
| `lexicon.py` | 中英双语时尚词表（Python 版，与 `auto.ts` 同源） |

### 5.9 语料库（`data/corpus/`）

三份文件，分别解决「叫什么」「怎么说」「怎么下判断」。

**`terms.json`　204 条术语**

| 字段 | 说明 |
|---|---|
| `zh` | 中文标准名，如「粗花呢」 |
| `en` | 英文对应，如 `tweed` |
| `aliases` | 别名，如 `bouclé`，用于合并同义统计 |
| `def` | 一句话定义，自己写，不抄 |
| `board` | 六个板块之一 |

为什么必须有别名字段：以前「薄纱 / 网纱 / 欧根纱」各算一条，同一篇文章会被重复计数三次；合并之后一条术语一次命中。

**`patterns.json`　24 个句式模板**

八类：转变、结构、搭配、色彩、论据、对比、收束、论点。每个模板带槽位、两个例句、一句使用场景。\n\n其中 24 条中文模板来自自有语料，6 条英文固有句式（P25–P30）来自 26 篇外部权威媒体的交叉验证，见 docs/句式验证.md。

```json
{ "id":"P03", "type":"shift", "template":"不再追求{A}，转而{B}",
  "slots":{"A":"被放弃的取向","B":"新的取向"},
  "examples":["不再思考还能往上加什么，转而思考还能去掉什么"] }
```

模板只定骨架，槽位由趋势或原文填充，避免整份报告一个腔调。

**`summary.json`　总述**

一句总论点、三段论据、一条反证、一句收束。每段挂的是**趋势名**，不是写死的数字——数字在渲染时从趋势里取。

**对应代码**

| 文件 | 作用 |
|---|---|
| `core/corpus.ts` | 读三份文件；把术语编译成正则（中文直配、英文加词边界）；提供计数函数 |
| `core/summary.ts` | 把人工论点接到趋势上，填出「刺绣 17 篇 34%」这样的数据行 |

## 6. 关键算法

### 6.1 三层去重

```ts
// normalize.ts
sameGroup && sim >= 0.85   → 同站不同版本，去掉
!sameGroup && sim >= 0.92  → 跨站转载，去掉
```

**为什么分三层**：同一个 URL 重复是手误；同一集团（Vogue US / UK / AU）发同题是编辑策略；不同站发同一篇是转载。三种都要去，但理由不同，报告里要分别标注。

标题相似度用 Jaccard：先把标题切成词集合，再算交集除以并集。

### 6.2 Wilson 区间

比例的标准误在小样本下不可靠，Wilson 用二次方程修正：

```
p̃ = (p + z²/2n) / (1 + z²/n)
半宽 = z·√(p(1-p)/n + z²/4n²) / (1 + z²/n)
```

z 取 1.96，对应 95%。好处是 n 小、比例接近 0 或 1 时不会给出负区间。

**为什么不用 p 值**：样本只有十几篇时，p 值几乎不可能显著；区间更诚实，能直接看出「区间重叠」。

### 6.3 置信度

```ts
enough = nA >= minN && nB >= minN
effect = |Δ| >= 5pp

high   = enough && !ciOverlap && effect && 同源占比 <= 30%
medium = enough && effect
low    = 其他
```

同源占比 = 转载/翻译/重复占比。这一条是防「十家媒体抄一篇」把结论吹大。

### 6.4 自动抽取

```
文章 → 切句 → 204 条术语命中 → 按板块聚合 → 取前 3 → 抽引用 → 挂图 → 填总述
```

关键参数：

- 词表来自 `data/corpus/terms.json`，含别名；中文直配，英文加词边界
- 门槛 `max(2, 文章数×6%)`：太少篇数的词不算趋势
- 每板块取 3 条：保证六个板块都有内容
- 「廓形」「版型」「结构」这类分析用语不进标题（META_TERMS）
- 引用优先不同来源：避免三句都来自同一家
- 共现词：和它同篇出现的其他词，用来生成词云和「常与…同篇出现」
- 总述：论点来自 `summary.json`，数据行由 `summary.ts` 按趋势名回填，找不到的趋势名会记进 `missing`

### 6.5 形状词云

```
1. 把轮廓栅格化成 3px 网格（心形/裙形/圆形）
2. 计算每个格子在不在轮廓内
3. 按到中心的距离给候选点排序
4. 从大到小放词：找到第一个放得下的位置就占位
5. 放不下就把字号缩小 16% 再试，最多四次
```

字号 `8 + 26 × √(n/maxN)`，字重 `300 + 400 × √(n/maxN)`。所以出现次数多的词又大又粗。

**为什么在构建时算**：不依赖浏览器 canvas，静态 HTML 打开就是最终效果，导出 PDF 也不会变。

### 6.6 阻尼滚动

```js
target += deltaY            // 累积目标位置
current += (target-current)*0.11   // 每帧插值
```

鼠标滚轮一次不是跳一段，而是给目标位置加一个偏移，画面再慢慢追上去。右下角可以关掉，系统开了「减少动态效果」时默认关闭。

## 7. 数据契约

### 7.1 文章（自动模式输入）

```json
{ "id": "A001", "title": "…", "url": "…", "date": "2026-10-05",
  "source": "Vogue Runway", "text": "正文", "image": "可选" }
```

### 7.2 证据（精细模式输入）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` / `sourceId` | 是 | 证据编号 / 来源编号 |
| `url` / `title` | 是 | 原文链接与标题 |
| `publishedAt` | 是 | `YYYY-MM-DD`，不知道填抓取日并置 `dateEstimated` |
| `season` / `window` | 是 | 主题季；A/B 进命题，X 只进台账 |
| `excerpt` | 是 | 从原文复制的一句话，禁止改写 |
| `codings` | 是 | 人工编码，如 `{"sheer": true}` |
| `originality` / `isSponsored` | 否 | 转载、品牌稿会拉低置信度 |

### 7.3 命题

时间窗 A/B、分析单位、最小样本量、编码规则、已知反证。**编码规则为空时审计直接报错，不出结论。**

## 8. 质量检查

16 类检查，分三级：

| 级别 | 代码 | 含义 |
|---|---|---|
| 错误 | `E_UNKNOWN_SOURCE` | 引用了不存在的来源 |
| 错误 | `E_SEASON_MISMATCH` | 季节与窗口不符 |
| 错误 | `E_UNFROZEN_RULE` | 命题没写编码规则 |
| 错误 | `E_NO_SUPPORT` | 结论没有支撑证据 |
| 错误 | `E_DANGLING_REF` | 引用了不存在的证据编号 |
| 警告 | `W_SMALL_N` | 样本不足 |
| 警告 | `W_SPONSORED_IN_SUPPORT` | 支撑里有品牌稿 |
| 警告 | `W_TIER3_DOMINANT` | 三级来源过半 |
| 警告 | `W_DUP_TITLE` | 疑似转载 |
| 警告 | `W_SHORT_EXCERPT` | 摘录过短，难复核 |
| 提示 | `I_CI_OVERLAP` | 区间重叠，幅度不稳 |
| 提示 | `I_DATE_ESTIMATED` | 发布日期是估算值 |
| 提示 | `I_DUP_URL` | 同 URL 重复，已剔除 |

出现「错误」时 `pnpm check` 退出码为 1，可以挂 CI。

## 9. 怎么扩展

**加一个信号**：在 `claims.json` 加一条命题，在证据里加同名 coding 键。代码不用动。

**加一个板块**：`taxonomy.json` 加一条，`auto.ts` 的 `BOARDS` 加一条，`magazine.ts` 的 `ACCENT` 加一个配色。

**加一个趋势词**：`auto.ts` 的 `TERMS` 加一行（中文、英文、板块、正则）。

**换一套版式**：只改 `render/magazine.ts`，分析层不受影响。

**换一批文章**：只换 `articles.json`，命令行参数 `--articles`。

## 10. 已知限制

1. **配图不贴题**：抓的是文章头图，整季合辑图和具体趋势可能对不上。
2. **中文站缺图**：多数是懒加载，抓不到。
3. **自动模式不做判断**：只说「24 篇提到」，不说「为什么」。
4. **词表有限**：52 个词之外的表达抽不到，需要人工补词。
5. **图片版权**：来自媒体，仅限内部演示。
6. **没有后端服务**：报告是静态文件，要动态分析得自己起服务（`pnpm serve` 还没做）。

## 11. 汇报建议

**三分钟版本：**

1. **问题**（30 秒）：趋势报告最大的问题是「说得像真的，但查不到」。我们的目标不是写得漂亮，是每句话都能回到原文。
2. **东西是什么**（30 秒）：一个命令行插件，输入一批文章，输出一份图文报告 + 一份 markdown + 一张证据表。
3. **演示**（90 秒）：打开 `reports/index.html`，点「自动模式」，展示一屏趋势：图、判断、词云、引用。再点一条引用，跳回原文。
4. **怎么保证不出错**（30 秒）：双重时间窗、区间不重叠才算高置信度、16 类自动检查、每条结论都能点到证据。

**可能被问到的问题：**

- *为什么不用大模型写？* → 会编。我们的验收标准是「内容准确、可复核」，模型写出来的句子没法逐句回链，所以只让机器做统计和摘句，判断留人工。
- *50 篇够吗？* → 够验证链路，不够下市场结论。报告里所有样本量都写在明面上。
- *和市面上的趋势报告差在哪？* → 他们好看，我们可查。图可以后补，证据链补不了。

## 12. 常见问题

**Q：为什么报告里看不到「XX 会火」这种话？**
A：预测需要比「媒体报道」更强的证据。我们现在只有媒体报道，所以只说「被提到多少次」，不说「会不会火」。

**Q：置信度为什么大多是「中」？**
A：样本 15–25 篇，比例接近 50% 时区间很宽，几乎必然重叠。这是样本量的限制，不是算法保守。

**Q：为什么有的趋势有数据箭头，有的没有？**
A：只有写了命题的趋势才有双时间窗对比。自动抽取的趋势没有命题，所以只显示词频和来源数。

**Q：图片能换成自己的吗？**
A：可以。`data/images.manifest.json` 记录每张图的来源，替换后重跑 `pnpm real` 即可。
